# 3D and WebGL: only when the concept needs it

**Read this only if the chosen concept calls for real-time 3D** (the test is in `concept.md` §2: the protagonist must turn in depth, be lit from moving angles, morph between volumes, or merge and split). Most premium sites need none: editorial type, real photography or procedural art, SVG and good motion carry them (a night-sky site can be a canvas of real stars and layered SVG ridges; a finance site can be paper and ink). Add WebGL when the concept's protagonist genuinely has to move, morph or be lit in 3D, and the brand can afford the weight.

**Don't clone a previous site.** These patterns came from one project with a jelly mascot; they are mechanics, not a look. Never default to a blobby mascot, a halo, ice-blue jelly or a "character holding the input" hero. Derive the protagonist, its material and its moves from this brand's concept (`concept.md`); if the concept has no character, there is no character.

When it is the right call, a real-time render makes the site unforgettable, but only if it stays fast, degrades gracefully and is wired into the DOM story. Pick the lightest technique that delivers the concept.

## 1. Choosing the technique
| Technique | Best for | Cost |
|---|---|---|
| CSS/SVG (layered shapes, transforms) | flat or illustrative mascots, icons that act | lowest |
| Image sequence scrubbed on a canvas | photoreal product rotations | bandwidth (lazy-load frames) |
| GLB in three.js / R3F | modelled products, rigged characters | ≤ 3MB compressed, after LCP |
| A raymarched SDF in one fragment shader | soft, jelly, liquid, blobby, morphing shapes; things that merge and split | GPU per pixel; no assets at all |

SDFs suit soft, liquid or morphing protagonists (only if that's what the concept is): smooth-union (`smin`) makes blobs merge with stretchy bridges, shapes morph by mixing distances, and the whole character is code (no model files). Keep the march inside bounding spheres/boxes, and compile rarely used shapes into separate shader variants so normal frames don't pay for them.

## 2. The layer sandwich: canvas between DOM layers
One fixed, full-screen, transparent canvas sits between each chapter's **back** layer (giant type, environments) and **front** layer (copy, UI):
```css
.world   { position: fixed; inset: 0; z-index: 2; pointer-events: none; }
.ch__back, .ch__front { position: sticky; top: 0; height: 100svh; overflow: clip; }
.ch__back  { z-index: 1; }
.ch__front { z-index: 3; margin-top: -100svh; pointer-events: none; }
.ch__front a, .ch__front button, .ch__front input, .ch__front textarea { pointer-events: auto; }
```
The protagonist can now stand *in front of* a giant word and *behind* the copy, which is what makes it feel like one scene. Use a premultiplied-alpha canvas so it composites cleanly over the page.

## 3. One world, many chapters
- **One renderer** for the page, one shared plain-object **scene** (camera, character, props) that timelines tween. Chapters never call the renderer; they tween the scene.
- Each chapter's choreography is a **keyframe script**: `[progress 0..1, snapshot]` pairs, built by merging small diffs into the previous snapshot so each chapter starts exactly where the last ended. See `scroll.md` → keyframe scripts and the "director".
- Add **"through" keys** that only key the groups they mention, so a gesture can change mid-chapter without stopping the camera.

## 4. Pinning DOM to 3D (labels, boxes, screens)
Give the renderer helpers and use them every frame (after it renders):
- `project(worldPoint) → {x, y, depth}` in CSS pixels: name tags that ride on characters, a graph centred inside a ring, tooltips on parts.
- `unproject(x, y, depth) → worldPoint` and `toLocal(worldPoint)`: make the character's hands grip the ends of a real DOM element (an input box), whatever the viewport.
- **Hands in front of a DOM box**: cut circular holes in the box's surface layer with a CSS mask at the projected hand positions (`mask: radial-gradient(circle r at x y, transparent, #000)` × 2 with `mask-composite: intersect`), so the canvas hands show through and appear in front. Keep the content inset so hands never cover controls.
- **A video or UI playing on a 3D surface**: project the surface's four corners and map a fixed-size DOM element onto them with a projective `matrix3d` (unit square → quad, Heckbert's method), `transform-origin: 0 0`. Fade it in once the morph completes. Reduce the surface's sway while content plays so it stays readable.
- Write styles only (transform, CSS variables, opacity); read at most one rect per frame.

## 5. Characters: states, gestures, acting
- Expose **named states** as numbers 0..1 (wave, point, think, celebrate, squint, hold, lean, squash, morph amounts) that timelines can blend, plus short **acts** (a greet, a cheer) that ease in and out over the timeline's values.
- **A rest pose that is truly at rest** (arms relaxed, a breath, blinking). A raised hand in the idle pose reads as an endless wave.
- **Gestures match the beat**: wave on the hello line, point toward the words being said (use the hand on the copy's side), squint at bad output, celebrate on success. Hover reactions only where the page invites them.
- **Eyes and gaze** sell life: follow the pointer softly in hero moments; look at the thing being discussed in story moments.
- **Transformations** tell the story: the character melts into a screen to show output, splits into a crew, pours letters out of its body and absorbs them back.

## 6. Same material everywhere (3D text and objects)
If the protagonist is made of a material (jelly, glass, chrome), render the hero wordmark and key props *in the same renderer and material* rather than as DOM approximations. Tube letters are cheap in an SDF (capsules + half-tori + tori); give each letter a centre, size and "shape" blend so it can grow from a blob on a strand out of the character and merge back in. Keep a flat DOM/SVG copy only as the no-WebGL fallback, plus a real `<h1>` for accessibility.

## 7. Performance guards
- **Lazy-load** the renderer after LCP or after the intro finishes; the hero copy and input render first.
- **Quality tiers** chosen from the device (GPU tier, memory, DPR, mobile): steps, samples, effects, frame cap.
- **Resolution scale** 0.6–0.8× capped DPR; soft visuals look identical and cost half.
- **Adaptive resolution**: if average frame time stays over budget, scale down in steps, then drop a tier.
- **Pause** when the tab is hidden (`visibilitychange`) and when the canvas is offscreen; resume cleanly.
- **Context loss**: `preventDefault` on `webglcontextlost`, rebuild programs on `webglcontextrestored`.
- **Reduced motion**: freeze time-based idle motion; keep scrubbed poses.
- **Measure** with a benchmark mode (N frames at fixed size, one read-back), alternated A/B runs.

## 8. Fallbacks and accessibility
- No WebGL → set `html[data-nowebgl]` and show a static/SVG version of the protagonist and wordmark.
- The canvas is `aria-hidden`; meaning lives in the DOM (real headings, labels, alt text).
- Never trap scroll or pointer in the canvas; it is `pointer-events: none` with DOM hit areas where needed.
