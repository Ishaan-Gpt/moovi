2. The promise (0:20-0:40)

3. Five days, measured (0:40-2:00)

a ranked bar chart builds, one bar per cause

I make stickman stories in 3D, with a cast of fifty characters living in bright pastel worlds. My last full episode ran seven and a half minutes, and it took me from Tuesday evening all the way to Sunday. So I asked Claude to read every timing log my sessions had kept and to rank whatever was eating the hours. The answer stung a little, because the slow part was never making the film, it was making it again. More than half of all the logged time went into fix rounds after a first cut already existed. One single clip went through six rounds with a judge, scoring five, then six, six, seven, seven, and then sliding back to six and a half. Second on the list was building looks and characters before any film even existed, which quietly swallowed whole evenings. Third was exporting the same film over and over, and one film alone was rendered from scratch nine times, which cost three hours by itself.

4. The machine twist (2:00-3:00)

a frame-time meter; then the same export shown twice side by side

Then Claude timed a single frame, and that's when I found out my laptop doesn't even have a proper graphics card. It only has the small chip built into the processor, so one frame of that busy stickman stadium takes about a fifth of a second to draw. It got stranger when I ran the very same export twice, ten minutes apart, and the timings didn't match at all. The first run took 224 milliseconds a frame and the second took 417, purely because something else on the machine was busy. So the first rule I learned was a cheap one, and I wish someone had told me sooner. Time one frame before you blame your code, because your computer might be the one holding you back.

5. The rulebook that learns (3:00-4:15)

the skill file scrolls, its updates ticking up; one correction turns into a rule

The real fix wasn't speed at all, though, it was taste, because most of those fix rounds repeated things I'd already said once. Claude would get a note from me, fix the shot, and then forget it completely by the next film. So now, whenever I say something is off, Claude writes it down as a rule in a skill file the same day. Muddy colours, a caption sitting on someone's face, a character doing a move the rig can't really pull off, all of it becomes a rule. That file has been updated more than ninety times so far, and every update is a mistake it won't make on me again. Before a single shot gets built, a small check reads the newest rules, looks at the plan and checks the computer itself. If the script isn't approved, the look isn't locked, or the disk is nearly full, it simply refuses to start. That one habit is the whole trick: every correction becomes a rule, or you end up paying for it twice.

6. The one-hour run (4:15-6:15)

a big clock in the corner; each step lights up as it starts

So I set a clock for one hour, gave Claude a single idea, and let it run the whole thing. It starts with the script, built around one clear rule and one danger you can see, because that's what keeps a stickman story easy to follow. Then it records the voice in one continuous take, so every shot can be timed to the exact word it belongs to. Next it pulls the cast, the sets and the camera moves from the kit it already owns, and that kit matters more than anything else here. The first time we made a film in this style without a kit, it took sixty-eight minutes just to reach a playable file. The second time, with the kit ready, the same step took seventeen minutes, which is when I stopped building things from scratch. After that, three builders work on separate scenes at once, each one owning its own files so nobody breaks anybody else's work. The moment a scene is finished, a fresh judge who has never seen our work scores a sheet of its frames out of ten. Anything under eight gets exactly one round of fixes, because a sixth round almost never beats the second. And each scene is exported the second it passes, so the render happens while the other scenes are still being built. RUN slot: what the clock showed at each step, one flowing sentence each

7. The fall (6:15-7:15)

the paper slip jumps between two frames; then the fix side by side

RUN slot: if the run broke somewhere real, that story goes here instead; otherwise this one And this is where it nearly fell apart, at the very last step, the one I thought was safe. To render faster, the export cuts the film into pieces and draws them side by side, then stitches them back together. Right at one of those stitches, a paper note in a girl's hand jumped to a different spot for a single frame. It turned out the film quietly remembers the frame before, so a piece that starts from nothing draws that moment slightly wrong. The fix was almost funny, because each piece now plays one second it will throw away before it starts recording. The jump vanished, and that frame went from a match score of 0.974 to 0.991, which is as close as video compression allows.

8. The self-correction (7:15-8:00)

I owe you one correction of my own, too, because I walked into this sure that rendering was the slow part. I had even told myself a faster computer would fix everything, and I was close to buying one. Once Claude actually measured it, rendering came in third, behind two problems no computer could ever solve for me. Those two were doing work twice and deciding things too late, and both of them were mine. RUN slot: our estimate before the run against the real time, said plainly in one sentence
